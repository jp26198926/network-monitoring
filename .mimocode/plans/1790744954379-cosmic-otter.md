# Monitor Custom/Public Node IPs — Plan

## Goal
Custom topology nodes with free-text IPs (e.g. public IPs like `8.8.8.8`) should show live status (up/down ring + latency) on the topology canvas, same as LAN device-bound nodes. **Auto-monitored** when an IP is set — no manual toggle. **Same cadence** as LAN (15s fast lane / 90s full sweep).

## Current gap
1. `monitor.js:rebuildTargets()` builds targets only from `subnet.usableHosts()` — no concept of external/extra IPs.
2. `probeOne()` skips creating a device row when a never-seen IP fails — so a permanently-down public IP never materializes.
3. `topology.js:refreshNodeStatuses()` skips nodes with `!node.deviceId` — never matches by `ip`.

## Approach
Monitor reads topology diagrams for custom IPs and probes them as **extra targets**. Topology page matches status by **IP fallback** for unbound nodes.

## Changes

### 1. `web/lib/monitor.js` — extra targets + unconditional row for extras
- Add `this.extraTargets = new Set()` to constructor.
- New method `refreshExtraTargets()`:
  ```js
  refreshExtraTargets() {
    this.extraTargets.clear();
    try {
      const store = require("./topology-store");
      for (const summary of store.list()) {
        const diagram = store.get(summary.id);
        for (const node of diagram?.nodes || []) {
          if (node.ip && node.ip.trim()) {
            this.extraTargets.add(node.ip.trim());
          }
        }
      }
    } catch { /* ignore */ }
  }
  ```
- Call `this.refreshExtraTargets()` at the top of `rebuildTargets()` and at the start of `fullSweep()` (cheap — reads cached JSON).
- `rebuildTargets()` after building subnet targets: `this.targets = [...usableHosts, ...this.extraTargets]` (dedupe).
- `probeOne(ip, ...)` change: when `!device && !result.ok`, if `this.extraTargets.has(ip)`, still `upsertDevice({ip, status:"down", ...})` instead of returning — so permanently-down custom IPs get a row and show red.

### 2. `web/public/topology.js` — IP-based status fallback
- Add `state.ipStatus = new Map()` — keyed by IP string → `{status, rttMs}`.
- Populate/update `ipStatus` wherever `liveStatus` is updated:
  - `loadDevices()` — for each device: `state.ipStatus.set(d.ip, {status: d.status, rttMs: null})`.
  - `handleWsMessage` `snapshot` — same for each device.
  - `device.up/down/update` — update both `liveStatus` and `ipStatus`.
  - `latency` — update `ipStatus` by `s.ip` too.
- `refreshNodeStatuses()`: for nodes **without** `deviceId` but **with** `ip`, look up `state.ipStatus.get(node.ip)` and apply ring + latency chip (same rendering as device-bound path).
- `refreshNodeLatencies()`: same IP fallback.
- Keep `deviceId` path as-is (takes priority when present).

### 3. No API / DB / WS changes
- `upsertDevice` already accepts any IP (no range check).
- WS events already carry `ip` on every payload.
- `topology-store` is already importable from `monitor.js` (same process).

## Files
| File | Change |
|---|---|
| `web/lib/monitor.js` | `extraTargets` set, `refreshExtraTargets()`, merge into `targets`, probeOne creates row for extras on failure |
| `web/public/topology.js` | `ipStatus` map, populate on load/WS, IP fallback in `refreshNodeStatuses` + `refreshNodeLatencies` |

## Verification
1. Start server, open `/topology`, create a custom node with IP `8.8.8.8` (no device binding), Save.
2. Within one fast-lane cycle (~15s), node shows **green** ring + latency chip.
3. Create another custom node with IP `10.255.255.1` (unreachable), Save → node shows **red**/unknown ring after 3 misses.
4. Change the IP in properties → status updates to the new IP's probe results.
5. Dashboard device list also shows these external IPs (they become device rows).
6. Restart server → custom nodes still show live status (targets re-collected from topology store).
